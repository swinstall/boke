## 一、从“手写工作流”到“学会工作流”

过去两年，多智能体系统的主流做法，是工程师手写一份调度逻辑：哪个模型负责规划、哪个负责写代码、哪个负责复查，彼此之间传什么上下文。这套东西本质上是一套精心设计的提示词工程加固定路由。它有两个问题：一是泛化差，换个任务分布就得重新调参；二是每一步都在消耗工程师的判断力，瓶颈不在模型，而在写编排的人。

Sakana AI 的 Conductor 论文（arXiv 2512.04388，ICLR 2026；Conductor 即“指挥家”，下文统一用 Conductor 指代）把这个问题换了个问法：编排本身能不能被训练出来？他们的做法是，用一个 Qwen2.5-7B 的小模型去“指挥”一池子更强的模型（GPT-5、Gemini 2.5 Pro、Claude Sonnet 4 以及几个开源模型），它不亲自解题，只负责输出“谁来干、干什么、谁能看到什么”。关键不在于这个 7B 模型有多聪明，而在于——当编排本身被训练成模型时，多智能体的瓶颈就从“提示词调参”转移到了“策略泛化”。

## 二、指挥家到底输出什么

Conductor 的接口极简，输出的是三个等长的 Python 列表（论文 §3.1，Appendix E）：

- model_id：每一步由哪个 worker 执行；
- subtasks：给这个 worker 的自然语言指令，也就是“元提示”；
- access_list：这个 worker 能看到哪些历史步骤的输出——可以是空、全部，或指定的步骤索引。

为什么重要：这三个列表各自对应一个传统多智能体框架里被硬编码的概念。model_id 取代了固定路由，subtasks 取代了手写 prompt，access_list 则直接定义了 agent 之间的通信拓扑——谁看得到谁的中间结果。论文里甚至给模型传入的是纯编号（Model 0、Model 1……），刻意隐藏模型名称，就是为了逼模型靠能力匹配而不是靠品牌先验来分配任务。

拿论文 Figure 2 里的真实示例来说，模型对一个“统计完全子数组个数”的题目输出 `model_id=[2,0]`、`subtasks=["设计一个高效算法统计完全子数组个数","用 Python 实现上一步 agent 给出的算法"]`、`access_list=[[], ["all"]]`——第一步让 2 号 worker 在不看任何历史的情况下独立设计算法，第二步让 0 号 worker 在全部历史上下文里用 Python 把算法实现出来。这个例子说明三个列表不是抽象约定，而是一条可直接执行、可回放、可审计的工作流。

执行上，工作流是顺序跑的，每一步把 access_list 允许的历史步骤塞进对应 worker 的上下文。这个表达能力足够覆盖 best-of-N、顺序链、树状并行。模型最大允许 5 步，实际平均只用 3 步——它自己学会了“难题多派几个人、简单题少折腾”。

## 三、奖励只认最终答案

训练这件事最反直觉的地方，是奖励信号极其粗糙：工作流最终输出等于标准答案就给 1 分，答错了给 0.5，三个列表解析不出来给 0 分（§3.1）。它完全不拆解“哪一步选对了 agent、哪条 prompt 写得好”，和 DeepSeek-R1 式的 RLVR 是同构的——只对最终结果赋权，不奖励过程。

算法是 GRPO，200 次迭代、批大小 256、2 块 H100 就收敛了，而且关闭了 KL 正则（KL 惩罚设为 0），reference model 同步也关掉。这意味着模型没有被任何“别偏离原始分布”的约束拉着，可以自由地重组解题策略。

更值得注意的是，规划-执行-验证（planner-executor-verifier）这个三段式结构并不是被写进代码的，而是训练后自发涌现出来的。在 LiveCodeBench 上，模型会先安排多轮 planning，再执行实现，最后做验证；代码难题上甚至会让 Gemini 2.5 Pro 和 Claude Sonnet 4 当高层规划，最后才让 GPT-5 写最终的优化代码。早期让 GPT-5 当 planner 的策略反而更差。

论文还给了两条短微调就能加上的扩展轴：一是自适应 worker 池，训练时对每个问题随机采样 worker 子集，让模型泛化到任意组合；二是递归自调用，允许 Conductor 把自己当 worker，看上一轮结果决定“再起一个新工作流还是直接返回”。不过递归这条的增益有限——平均分从 61.93 提到 63.00，主要来自 BigCodeBench 的 37.8 到 40.0，收益集中且幅度不大。

## 四、实测数字与对照

下面是主结果（论文 Table 1，Unconstrained 口径），并注明每个数字的实验条件：

| 指标 | Conductor(7B) | GPT-5 | Gemini 2.5 Pro | Claude Sonnet 4 | 说明 |
|---|---|---|---|---|---|
| LiveCodeBench V6 | 83.93 | 82.90 | 67.24 | 46.54 | 未见题代码基准，论文称超越当时榜单所有模型 |
| GPQA-Diamond | 87.5 | 82.3 | 84.8 | 77.7 | OOD 科学问答 198 题 |
| AIME25 | 93.3 | 90.8 | 78.3 | 74.3 | OOD 竞赛数学 30 题 |
| MMLU | 94.1 | 93.5 | 92.4 | 91.4 | in-domain 事实知识 |
| 七任务平均 | 77.27 | 74.78 | 70.97 | 65.69 | 表 1 七项任务（MATH500、MMLU、RLPR、LiveCodeBench、AIME25、BigCodeBench、GPQA-D）算术平均 |

实验条件说明（重要）：这些数字是 unconstrained 口径，即各模型都用最大推理或输出预算，取自有复现、私有实现和在线榜单里的最高记录；每项评测按题量重复至多 16 次，报告 mean accuracy 加标准误。因此它不是单次运行的原始分，论文正文也没有使用 pass@1 字样。读者引用时需注意这是 unconstrained 口径、非单次运行分；官方博客转述的 83.9% 与论文的 83.93% 是同一数字的取整。

更值得看的是同池受控对比（Table 7，Constrained 口径，所有 agent 限 4096 tokens、推理预算取最小，这正是训练时的设置）：Conductor 平均 72.35，Mixture-of-Agents 62.13，5 轮自反思（GPT-5）64.52，而单模型跑 GPT-5 只有 63.72。也就是说，即便把各家拉到同一预算下，编排仍然带来了稳定收益，而不是靠堆更多模型推理量刷出来的。

成本维度同样反直觉：Conductor 平均每题 1820 tokens、约 0.0238 美元，MoA 是 11203 tokens、约 0.0486 美元。一个 7B 的小模型指挥一群大模型，居然比让大模型之间互相叠加更省、也更强。

## 五、工程含义：什么时候值得学策略层

这套工作最值得工程团队借鉴的，不是“再叠一个 7B 模型”，而是它划出的判断边界。什么时候值得去训练或学习一个策略层，什么时候继续老老实实调 API，可以用几个可操作的标准：

- 任务分布稳定且高频：比如固定的客服分诊、固定的代码审查流程——这类场景编排的价值可以复用，值得投入策略层。
- 需要跨模型动态调度、且模型池会变：比如要在 GPT-5、Claude、Gemini 之间按能力和成本动态选择，硬编码路由很快失效，学出来的调度更抗供应商变动。
- 一次性或长尾任务：编排价值无法摊销，继续调 API、手写 prompt 是更划算的选择。
- 容错要求极高、过程可解释性必须强：手写工作流每一步可见可改，比黑盒学出来的编排更可控。

一句话收束：当“编排”本身被训练成一个模型，多智能体系统的瓶颈就从提示词调参转移到了策略泛化——模型不再是你写死的那套固定流程，而是学会“如何组队”的一层能力。
